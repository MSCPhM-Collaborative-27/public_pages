1Introduction

1.1The goal

This repository is a shared space for the cohort to collaborate on lecture notes, slides, and questions across the PHM modules, instead of everyone taking notes alone and losing them at the end of the semester.

Precision medicine is a young field, and a lot of what you'll read about it is scattered, or outright conflicting. One set of notes that several people have read, corrected, and signed off on is more reliable than anyone's solo notes — the same reason research goes through peer review. That's why every change here is reviewed before it lands (§3.2): the review isn't bureaucracy, it's what makes the notes trustworthy.

What that means in practice:

  • Notes get annotated collaboratively. If someone's note on a topic is unclear or incomplete, improve it directly — don't start a separate version elsewhere.
  • If you miss a class, the notes should cover most of what you missed.
  • Contributing is optional. You can read and use everything on main without ever sharing your own notes back — see §1.5.

1.2Read, fix, or contribute?

Not everyone needs the whole guide. Find yourself below and read only what applies.

Path AI just want to read the notes

You don't need to install anything, and you don't need Git. Once you have access (§1.5), everything on main is browsable at github.com in an ordinary browser:

  • Open the repository and click into any module folder — §1.3 shows what's where.
  • Click a .md file and it renders formatted — headings, tables, and lists display properly, not as raw text.
  • The branch switcher above the file list lets you peek at anyone's in-progress branch, not just main.

That's the entire workflow for reading. Nothing past this page is required.

Path BI want to fix a typo or add something small

GitHub's web editor handles this without installing anything:

  1. Browse to the file on github.com and click the pencil icon (Edit this file), top-right of the file view.
  2. Make your change in the browser.
  3. Click Commit changes… and choose Create a new branch and start a pull request — GitHub creates the branch and opens the PR for you.

To add a new small file instead: navigate to the right folder (§1.3), then Add file → Create new file. Either way your change goes through the same review as everything else (§3.2) — this is a lighter path to the same gate, not a way around it.

Path CI want to contribute regularly

Do the one-time setup in §2 (VS Code, Git, clone — budget about an hour), then follow the workflow in §3. The start-to-finish walkthrough in §3.1 shows the whole loop on one screen; §4.1 has ideas for what to contribute.

1.3How the repo is organised

The root has one folder per core module, plus elective_courses/ for the rest. Every module folder has the same four subfolders:

courses_and_notesharing/
├── PHM5001/                one folder per core module
│   ├── slides/             lecture slides, as given
│   ├── notes/              collaborative Markdown notes
│   ├── questions/          practice questions & worked solutions
│   ├── personal/           your private scratch space — gitignored, never shared
│   └── README.md           module synopsis & topic list
├── PHM5002/ … PHM5006/     same shape
└── elective_courses/
    └── PHM5007/ … PHM5016/ same shape again

Naming files. A typical note file looks like PHM5001/notes/lecture-03-variant-calling.md. The convention:

  • Lowercase, hyphens instead of spaces — no Final Notes (2).md.
  • Notes tied to one lecture start with lecture-NN- (two digits, so files sort in order), followed by a short topic.
  • One file per lecture or topic, not one running file for the whole module — small files merge cleanly and are easier for the next person to extend.
  • Slides keep whatever filename the lecturer gave them; questions get a short descriptive name like tutorial-02-solutions.md.

1.4Code of conduct

  • Flag uncertainty. A note that says "not sure this is right" is more useful than a confident note that's wrong.
  • Don't redistribute. This repo is whitelisted to protect NUS's IP. Notes, slides, and questions stay inside the group.
  • Attribute, don't copy. Summarise lectures, papers, and textbooks in your own words. Don't paste in copyrighted material wholesale.
  • Disagree in the open. If a note looks wrong, say so in a PR comment or a Discussion thread. Don't silently rewrite someone else's work without explanation.
  • No unverified AI output. Full detail in §4.4 — short version: if you didn't check it against the actual lecture, it isn't ready to merge.

1.5Access & expectations

  1. Reach out to whoever is coordinating this repo to be added — both to the GitHub repository and to wherever the group organises itself (chat, email thread, or otherwise).
  2. To read: that's it, no GitHub experience required — see Path A above.
  3. To contribute: a small fix needs nothing but a browser (Path B). For regular contributing, follow the setup in §2 and the workflow in §3 — budget an hour or two the first time; nobody's expected to arrive already knowing Git.

Once you're in: read §1.4, keep contributions in the format described in §4.3, and don't share access or content outside the group.
